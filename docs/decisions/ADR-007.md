# ADR-007: Función SECURITY DEFINER para lookup de login — excepción acotada a RLS de `Personal`

**Estado:** Aceptado
**Fecha:** 2026-08-04

## Contexto

Las políticas RLS de `personal` (`db/ddl_mvp.sql`, ver también ADR-006)
dependen de dos valores de sesión que el backend fija por request, después
de autenticar:

```sql
SET app.current_rol = '<rol>';
SET app.current_personal_id = '<id_personal>';
```

`personal_select` es:

```sql
USING (
    app_current_rol() IN ('directivo', 'admin')
    OR id_personal = app_current_personal_id()
)
```

El flujo de login (`email_institucional` + `password` → verificar contra
`password_hash` → emitir JWT) necesita leer la fila de `Personal` que
corresponde a ese email **antes** de que exista ningún JWT — es decir,
antes de que el backend pueda saber qué `SET` ejecutar. En ese momento
`app.current_rol` y `app.current_personal_id` nunca se fijaron en la
sesión, así que `current_setting(..., true)` devuelve `NULL` en ambos.
`NULL IN (...)` y `id_personal = NULL` son `NULL`, el `OR` de dos `NULL` es
`NULL`, y Postgres trata eso como `false` en una cláusula `USING` — el
diseño fail-closed que ya está documentado explícitamente en el DDL.

El resultado es que, con el rol de runtime `sige_app` (sin bypass de RLS,
por diseño de ADR-006), **la consulta de login no devuelve ninguna fila
para nadie**, credenciales válidas incluidas. Es un huevo-gallina real: la
identidad de sesión que RLS necesita para autorizar la lectura es
precisamente lo que la lectura de login está tratando de establecer.

### Por qué las alternativas de ADR-006 no aplican aquí

ADR-006 ya evaluó y descartó, para el problema general de runtime vs.
migraciones, las dos rutas que servirían para bypassear esto:

- **Conectar como `sige_migrator` (owner)**: es la regla dura explícita de
  ADR-006 — "el backend en runtime NUNCA debe conectarse con
  `sige_migrator`". Usarlo aquí, aunque fuera solo para el login, reabre
  exactamente el escenario que ADR-006 documentó como inseguro (RLS
  bypasseada en silencio), y además el bypass no quedaría acotado a login:
  cualquier query hecha con esa conexión ve todo.
- **Un tercer rol de Postgres con más privilegios que `sige_app`**: ADR-006
  ya lo descartó explícitamente para el MVP ("no hay necesidad hoy de un
  privilegio de Postgres adicional"). Agregar un rol nuevo solo para este
  caso sería reabrir esa decisión sin una razón que ADR-006 no haya
  considerado ya.

Tampoco es aceptable relajar la política RLS en sí (ej. agregar
`OR app_current_rol() IS NULL`): eso no acota el bypass al login, sino que
lo abre a **cualquier** bug del backend que olvide hacer el `SET` antes de
consultar `personal` — convertiría un fail-closed intencional (documentado
en el DDL) en fail-open silencioso para el caso más sensible (login).

## Decisión

Se agrega una función Postgres `fn_login_lookup(p_email)` con
`SECURITY DEFINER`, cuyo único propósito es resolver esta lectura puntual
de login. Propiedades, todas deliberadas:

- **Solo lectura.** `LANGUAGE sql` (no `plpgsql`), un único `SELECT` — no
  puede contener ninguna sentencia de escritura por construcción del
  lenguaje.
- **Parámetro tipado** (`p_email VARCHAR(100)`, el mismo tipo que
  `personal.email_institucional`), nunca interpolación de string — el
  llamador (`app/core/security.py`) debe invocarla con un parámetro
  ligado (`:email`), no con `f"...{email}..."`.
- **Filtra `estatus = 'activo'` dentro de la función.** Un `Personal` dado
  de baja no debe poder autenticarse aunque conozca su password — esta
  regla vive en la función, no delegada al service, para que no dependa
  de que cada llamador la reimplemente correctamente.
- **Devuelve únicamente** `id_personal, rol, password_hash, estatus` — no
  la fila completa (nada de `curp`, `nombre`, `email_institucional`,
  `telefono`, etc.). Es exactamente lo que el flujo de login necesita para
  verificar el password y emitir el JWT; no una forma alterna de leer
  `Personal` completo.
- **`SET search_path = public`** fijo en la definición de la función, para
  cerrar el vector clásico de "search_path hijacking" sobre funciones
  `SECURITY DEFINER` (que corren con los privilegios del *owner*, no del
  invocador).
- **`REVOKE ALL ... FROM PUBLIC` + `GRANT EXECUTE ... TO sige_app`
  explícito.** Postgres otorga `EXECUTE` a `PUBLIC` por defecto al crear
  una función; se revoca y se otorga solo a `sige_app`. Ningún otro rol
  (ni siquiera uno hipotético futuro) puede invocarla sin un `GRANT`
  explícito nuevo.
- **Dueña de la función: `sige_migrator`**, igual que las tablas — se crea
  en la migración de Alembic, que corre con ese rol. `SECURITY DEFINER`
  hace que la función se ejecute con los privilegios de su *owner*, y un
  owner de tabla no está sujeto a RLS sobre esa tabla (el mismo
  comportamiento de Postgres que motivó ADR-006 en primer lugar) — por
  eso esta función sí puede leer `personal` sin que aplique
  `personal_select`, de forma controlada y exclusivamente para este caso.

**Esta función no es un patrón general para bypassear RLS.** Es una
excepción puntual, documentada, para el único caso donde la identidad de
sesión que RLS necesita todavía no existe. Cualquier otro caso futuro que
"necesite saltarse RLS" (batch jobs, reportes administrativos, lo que sea)
requiere su propia discusión y su propio ADR — no debe justificarse
apuntando a este.

## Alternativas descartadas

- **Conectar como `sige_migrator` para el login**: ver arriba — contradice
  la regla dura de ADR-006 y el bypass no queda acotado a esta query.
- **Tercer rol de Postgres con privilegio de lectura sin RLS**: ya
  descartado por ADR-006 para el MVP; y de todos modos no resolvería el
  problema de raíz (seguiría siendo una conexión completa sin RLS, más
  amplia que "una función puntual").
- **Relajar `personal_select` para permitir lectura sin sesión**: convierte
  el fail-closed documentado en fail-open ante cualquier bug de backend
  que omita el `SET` — inaceptable para la tabla que contiene
  `password_hash`.
- **Resolver el login completamente en la capa de aplicación (ORM sin
  RLS)**: implicaría que `sige_app` sea owner o tenga `BYPASSRLS`, lo cual
  vuelve a abrir RLS para todas las demás queries del mismo rol — el
  problema que ADR-006 ya resolvió no debe reabrirse para arreglar un caso
  puntual.

## Consecuencias

- `db/ddl_mvp.sql` gana `fn_login_lookup` junto a los helpers de RLS
  existentes (`app_current_rol`, `app_current_personal_id`), como
  referencia del esquema completo actual.
- Se agrega una migración de Alembic nueva (no se reescribe
  `7460fa835be8`) que crea la función y su `GRANT` — ver
  `app/db/migrations/versions/`.
- `app/core/security.py` es el único código de aplicación autorizado a
  invocar `fn_login_lookup`, y solo durante el flujo de login. No debe
  usarse para ninguna otra lectura de `Personal`.
- La batería de validación de Fase 0/1 (RLS con `sige_app`) se repite y se
  extiende para esta función — ver `docs/validacion/` — confirmando que
  login funciona para un usuario activo, falla para uno dado de baja, y
  que el resto de las políticas RLS de `personal` (Nivel 1/2 de la matriz
  RBAC) permanecen intactas.
