# ADR-010: Reporte_Incidencia — scope de creación sin `grupo_asignatura`, y excepción `SECURITY DEFINER` para búsqueda de alumno por docente

**Estado:** Aceptado
**Fecha:** 2026-08-15

## Contexto

`Calificacion` y `Asistencia` comparten el mismo patrón de scope para
`docente`: solo pueden operar sobre alumnos que están en uno de sus
propios `grupo_asignatura` (matriz RBAC Nivel 2, `docs/rbac/matriz-rbac-mvp.md`).
Ese patrón está reforzado en RLS con un `IN (SELECT id_grupo_asig FROM
grupo_asignatura WHERE id_docente = app_current_personal_id())`.

Se pidió construir `Reporte_Incidencia` (diseño cerrado en
`docs/data_dictionary/reporte-incidencia.md`) con una regla distinta a
propósito: **cualquier `Personal` con `rol='docente'` y
`estatus='activo'` puede crear un reporte sobre cualquier alumno del
plantel**, sin exigir relación vía `grupo_asignatura`. Esto contradice el
patrón de scope ya establecido para las otras dos entidades de captura
docente, así que se documenta aquí el porqué (regla de `CLAUDE.md`: no
contradecir un patrón ya establecido sin señalarlo).

## Decisión

### 1. `reporte_incidencia_insert` sin join a `grupo_asignatura`

```sql
CREATE POLICY reporte_incidencia_insert ON reporte_incidencia
    FOR INSERT
    WITH CHECK (
        app_current_rol() = 'docente'
        AND id_personal_reporta = app_current_personal_id()
        AND EXISTS (
            SELECT 1 FROM personal
            WHERE id_personal = app_current_personal_id()
              AND estatus = 'activo'
        )
    );
```

Sin ningún filtro sobre `id_alumno` — cualquier docente activo puede
reportar sobre cualquier alumno del plantel. `id_personal_reporta =
app_current_personal_id()` sigue siendo obligatorio (anti-suplantación,
mismo propósito que `asistencia_insert`/`auditoria_calificacion_insert`),
y además el `EXISTS` contra `personal.estatus` es una verificación
explícita en la tabla real, no solo el claim `rol` del JWT — defensa en
profundidad: el JWT se emite al login y no se revalida contra
`Personal.estatus` en cada request (`get_current_personal`,
`app/core/security.py`, no vuelve a leer la tabla), así que un docente
dado de baja después de emitido su token seguiría pasando
`require_roles("docente")` en la capa HTTP hasta que expire. La política
RLS es quien realmente cierra ese hueco.

### 2. `reporte_incidencia_select`: scope por autor, no por `grupo_asignatura`

```sql
CREATE POLICY reporte_incidencia_select ON reporte_incidencia
    FOR SELECT
    USING (
        app_current_rol() IN ('directivo', 'admin')
        OR id_personal_reporta = app_current_personal_id()
    );
```

Un docente ve solo los reportes que él mismo levantó — no los de otros
docentes sobre el mismo alumno. `directivo`/`admin` ven todo el plantel,
igual que en `Calificacion`/`Asistencia`.

### 3. Tabla inmutable

Sin políticas de `UPDATE`/`DELETE` — Postgres deniega esas operaciones
por defecto a cualquier rol no-owner/no-superuser, incluido `admin`,
mismo patrón ya validado con `Auditoria_Calificacion` (Fase 5). Sin
endpoints `PUT`/`DELETE` tampoco.

### 4. `fn_alumno_buscar_docente` — excepción `SECURITY DEFINER` nueva

El scope normal de lectura de `Alumno` para un docente (`alumno_select`)
sigue acotado a sus propios `grupo_asignatura` — **esta ADR no lo
cambia**. Pero la pantalla de captura de `Reporte_Incidencia` necesita
que el docente pueda *buscar* un alumno fuera de ese scope para poder
reportarlo. Reutilizar `GET /alumno?search=` tal cual no sirve: seguiría
acotado por `alumno_select`.

Se agrega una función nueva, siguiendo el mismo patrón ya discutido y
aceptado en ADR-007 (`fn_login_lookup`) — el comentario en
`db/ddl_mvp.sql` junto a `fn_login_lookup` advierte explícitamente que
ese patrón "no es reutilizable sin la misma discusión"; esta ADR es esa
discusión:

```sql
CREATE OR REPLACE FUNCTION fn_alumno_buscar_docente(p_search VARCHAR)
RETURNS TABLE (
    id_alumno         INT,
    matricula         VARCHAR(20),
    nombre            VARCHAR(80),
    apellido_paterno  VARCHAR(60),
    apellido_materno  VARCHAR(60)
)
SECURITY DEFINER
SET search_path = public
LANGUAGE sql
STABLE
AS $$
    SELECT a.id_alumno, a.matricula, a.nombre, a.apellido_paterno, a.apellido_materno
    FROM alumno a
    WHERE app_current_rol() = 'docente'
      AND (
        concat_ws(' ', a.nombre, a.apellido_paterno, a.apellido_materno) ILIKE '%' || p_search || '%'
        OR a.curp = upper(p_search)
      );
$$;

REVOKE ALL ON FUNCTION fn_alumno_buscar_docente(VARCHAR) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION fn_alumno_buscar_docente(VARCHAR) TO sige_app;
```

Acotada de forma deliberada, igual que `fn_login_lookup`:
- Solo devuelve resultados cuando `app_current_rol() = 'docente'` (el
  `WHERE` interno de la función, no solo `require_roles` en FastAPI) —
  para cualquier otro rol devuelve 0 filas, no un error.
- Campos mínimos de identificación únicamente (`id_alumno`, `matricula`,
  `nombre`, `apellido_paterno`, `apellido_materno`) — nada de lo que
  Nivel 3 de la matriz RBAC ya restringe a docente en `AlumnoOutDocente`
  (`curp`, `fecha_nacimiento`, `email`, `telefono_personal`,
  `municipio_origen`, `localidad_origen` quedan fuera).
- No modifica `alumno_select` ni ninguna política existente — es una
  función nueva, de un solo propósito (`GET /alumno/buscar-plantel`),
  no una puerta trasera genérica a `Alumno`.

## Razón

El negocio pidió esta feature con la regla de scope explícitamente
distinta a `Calificacion`/`Asistencia`: una incidencia de conducta o
disciplina puede presenciarla cualquier docente del plantel (pasillo,
receso, evento escolar), no solo quien imparte clase a ese alumno —
exigir relación vía `grupo_asignatura` bloquearía el caso de uso real
que motiva la feature.

## Alternativas descartadas

- **Ampliar `alumno_select` para que docente vea todo el plantel**:
  descartado — resolvería la búsqueda pero rompería el scope ya
  validado y probado de `Alumno`/`Calificacion`/`Asistencia` para
  docente en absolutamente todas las demás pantallas, mucho más amplio
  que lo que este caso de uso necesita.
- **Exigir `grupo_asignatura` también para `Reporte_Incidencia`**:
  descartado por el propio negocio — contradice el caso de uso real
  (incidencias fuera del salón de clase).
- **Endpoint de búsqueda sin `SECURITY DEFINER`, filtrando en Python
  después de traer todo `Alumno`**: descartado — traería de vuelta
  filas fuera del scope RLS del docente a la capa de aplicación antes de
  filtrar, exponiendo más superficie de la necesaria si hay un bug en el
  filtro de Python. La función `SECURITY DEFINER` deja que sea Postgres
  quien decida qué columnas salen, no una capa de aplicación que podría
  fallar.

## Consecuencias

- `Reporte_Incidencia` es la primera entidad del sistema donde `docente`
  tiene alcance de escritura sobre *todo* el plantel, no solo su propio
  scope — cualquier feature futura que reutilice este patrón debe
  repetir esta misma discusión explícita, no asumir que ya es el
  default.
- `fn_alumno_buscar_docente` es de un solo propósito: si aparece otro
  caso de uso que necesite que un docente busque fuera de su scope, se
  evalúa aparte si conviene generalizar esta función o crear una nueva
  — no se debe ampliar esta sin revisar el caso de uso original.
