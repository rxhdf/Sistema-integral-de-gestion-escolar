# ADR-011: `fn_registrar_intento_login` — función separada de `fn_login_lookup` para el log de accesos

**Estado:** Aceptado
**Fecha:** 2026-08-16

## Contexto

`Gestión de Cuentas` (diseño cerrado en
`docs/data_dictionary/gestion-cuentas.md`, Pieza 3) pide un historial
completo de intentos de login, exitosos y fallidos, en una tabla nueva
`log_acceso`. El propio documento de diseño plantea el mismo huevo-gallina
que resolvió ADR-007 (`fn_login_lookup`): el login ocurre antes de que
exista sesión con `app.current_rol`/`app.current_personal_id` fijados, así
que cualquier INSERT normal desde `sige_app` sobre `log_acceso` (con RLS
habilitado) sería denegado por diseño fail-closed — necesita el mismo
mecanismo `SECURITY DEFINER`.

El documento de diseño deja abiertas dos opciones y pide decidir con
Claude Code:

- (a) Ampliar `fn_login_lookup` para que también inserte el log.
- (b) Una función separada, `fn_registrar_intento_login`, llamada desde el
  mismo flujo de autenticación en el service de FastAPI.

## Decisión

Se elige **(b): función separada**, `fn_registrar_intento_login(p_email,
p_exitoso)`. Razones, todas derivadas de invariantes que ADR-007 ya dejó
explícitas para `fn_login_lookup` y que ampliarla rompería:

1. **`fn_login_lookup` está documentada en ADR-007 como "solo lectura"
   por construcción del lenguaje** (`LANGUAGE sql`, un único `SELECT`,
   "no puede contener ninguna sentencia de escritura por construcción del
   lenguaje"). Esa propiedad no es incidental — es parte de por qué se
   aceptó la excepción `SECURITY DEFINER` en primer lugar: una función que
   solo puede leer es una superficie de ataque mucho más pequeña que una
   que también escribe. Convertirla en una función que también inserta
   significaría (a) cambiar `LANGUAGE sql` a `plpgsql` y (b) revisar otra
   vez todo el razonamiento de ADR-007 bajo un perfil de riesgo distinto,
   sin necesidad real de tocar esa función para lograr el objetivo de esta
   feature.

2. **`fn_login_lookup` filtra `estatus = 'activo'` dentro de su propio
   `WHERE`** — así que cuando no hay fila, no se puede distinguir desde
   Python si el email no existe, existe pero está `bloqueado`, o existe
   pero está de `baja`. El log necesita justamente esa distinción para
   poblar `motivo_fallo` (`credenciales_invalidas` / `cuenta_bloqueada` /
   `cuenta_baja`, ver diccionario de datos). Pedirle esa distinción a
   `fn_login_lookup` requeriría relajar su propio filtro (cambiar su
   contrato ya validado en Fase 0/1) o devolver más columnas de las que
   el flujo de autenticación necesita — ambas cosas amplían el propósito
   de una función que ADR-007 fijó deliberadamente acotada a un solo caso
   de uso.

`fn_registrar_intento_login` resuelve la distinción de `motivo_fallo`
haciendo su propia lectura interna de `personal` (sin el filtro de
`estatus = 'activo'`) — igual que `fn_login_lookup`, corre como
`SECURITY DEFINER` y por tanto bypassea RLS de forma acotada y
controlada, exactamente el mismo patrón que ADR-007 ya aceptó, solo que
para un propósito distinto: no autenticar, sino clasificar el motivo de
un evento que la autenticación ya resolvió.

```sql
CREATE OR REPLACE FUNCTION fn_registrar_intento_login(p_email VARCHAR(100), p_exitoso BOOLEAN)
RETURNS VOID
SECURITY DEFINER
SET search_path = public
LANGUAGE plpgsql
AS $$
DECLARE
    v_id_personal INT;
    v_estatus     VARCHAR(20);
    v_motivo      VARCHAR(50);
BEGIN
    SELECT id_personal, estatus INTO v_id_personal, v_estatus
    FROM personal
    WHERE email_institucional = p_email;

    IF NOT p_exitoso THEN
        IF v_id_personal IS NULL THEN
            v_motivo := 'credenciales_invalidas';
        ELSIF v_estatus = 'bloqueado' THEN
            v_motivo := 'cuenta_bloqueada';
        ELSIF v_estatus = 'baja' THEN
            v_motivo := 'cuenta_baja';
        ELSE
            v_motivo := 'credenciales_invalidas';
        END IF;
    END IF;

    INSERT INTO log_acceso (email_intentado, id_personal, exitoso, motivo_fallo)
    VALUES (p_email, v_id_personal, p_exitoso, v_motivo);
END;
$$;
```

Propiedades deliberadas, mismo patrón que `fn_login_lookup`:

- **Nunca recibe la contraseña intentada**, ni en texto plano ni hasheada
  — solo `p_email` y `p_exitoso` (un booleano que `app/core/security.py`
  ya calculó comparando el hash). El diccionario de datos es explícito en
  que la contraseña intentada nunca se guarda; al no pasarla como
  parámetro, ni siquiera transita por esta función.
- **`SET search_path = public`** fijo, mismo cierre de search_path
  hijacking que ADR-007.
- **`REVOKE ALL ... FROM PUBLIC` + `GRANT EXECUTE ... TO sige_app`
  explícito**, mismo patrón.
- **Dueña de la función: `sige_migrator`** — corre con sus privilegios
  (`SECURITY DEFINER`), por eso puede insertar en `log_acceso` aunque
  `sige_app` no tenga ninguna política RLS de `INSERT` sobre esa tabla
  (validado directamente con `sige_app`: un INSERT directo a `log_acceso`
  es rechazado por RLS incluso para `admin`, ver
  `docs/validacion/gestion-cuentas.md`).
- **Único llamador autorizado:** `app/core/security.py::authenticate_personal`,
  igual que `fn_login_lookup` — no debe usarse para ninguna otra escritura.

### Commit explícito en `authenticate_personal`

Detalle de integración que no es parte del diseño de la función SQL en sí,
pero es necesario para que el log capture también los intentos
**fallidos**: `app/core/session.py::get_db` hace `db.commit()` una sola
vez, al final del request, y `db.rollback()` si el handler propaga una
excepción. `/auth/login` (`app/domains/personal/router.py`) levanta
`HTTPException(401)` cuando el login falla — eso dispara el `rollback()`
de `get_db`, que se llevaría con él la fila de `log_acceso` recién
insertada para ese mismo intento fallido, justo el caso que este log más
necesita capturar. Por eso `authenticate_personal` hace un `db.commit()`
explícito inmediatamente después de llamar a
`fn_registrar_intento_login`, antes de devolver `None` o el
`LoginResult` — a esa altura del flujo todavía no se fijó ningún
`app.current_rol`/`app.current_personal_id` (ADR-007), así que el commit
temprano no interfiere con nada más.

## Alternativas descartadas

- **Ampliar `fn_login_lookup`**: descartada — ver los dos puntos de
  "Decisión" arriba (rompe la invariante "solo lectura" de ADR-007 y
  necesitaría relajar su filtro `estatus = 'activo'`, dos cambios a una
  función ya validada en Fase 0/1 sin necesidad real).
- **Registrar el log desde Python sin `SECURITY DEFINER`** (INSERT directo
  vía `sige_app`): descartado — mismo huevo-gallina de ADR-007, RLS
  denegaría el INSERT en el momento del login (sin sesión) igual que
  denegaría el SELECT de `personal` por email.
- **Pasar `motivo_fallo` ya calculado desde Python** (en vez de que la
  función lo derive internamente): descartado — para calcularlo en Python
  haría falta que `authenticate_personal` ya supiera el `estatus` de una
  cuenta inactiva, información que `fn_login_lookup` deliberadamente no
  expone (filtra `estatus = 'activo'` en su propio `WHERE`). Dejar que
  `fn_registrar_intento_login` haga su propia lectura interna evita tener
  que ampliar lo que `fn_login_lookup` devuelve.

## Consecuencias

- `db/ddl_mvp.sql` gana la tabla `log_acceso` (con RLS) y
  `fn_registrar_intento_login`, documentadas junto a `fn_login_lookup` y
  `fn_alumno_buscar_docente`.
- Migración incremental de Alembic:
  `app/db/migrations/versions/23e24f6cd81d_log_acceso_table_rls_and_fn_registrar.py`.
- `app/core/security.py::authenticate_personal` es el único código de
  aplicación autorizado a invocar `fn_registrar_intento_login`.
- Cualquier caso futuro que quiera registrar más eventos de seguridad
  (ej. cambios de contraseña, intentos de acceso a rutas prohibidas) debe
  evaluarse aparte — esta función es de un solo propósito (intentos de
  login), no un logger genérico de eventos de seguridad.
