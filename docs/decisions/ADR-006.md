# ADR-006: Separación de roles de conexión a Postgres (migraciones vs. runtime)

**Estado:** Aceptado
**Fecha:** 2026-07-29

## Contexto

Row-Level Security (RLS) en PostgreSQL no se aplica al *owner* de la tabla
ni a ningún rol `SUPERUSER`, sin importar cuántas `CREATE POLICY` existan
(`ALTER TABLE ... FORCE ROW LEVEL SECURITY` solo fuerza RLS sobre el owner,
nunca sobre un superuser). Esto se validó de forma práctica al levantar
`db/ddl_mvp.sql` en Postgres 16: ejecutando las queries como el rol
`postgres` (superuser, dueño de las tablas por haber corrido el DDL), todas
las políticas de `docs/rbac/matriz-rbac-mvp.md` se ignoran silenciosamente
— cualquier rol ve y escribe todo. Las mismas queries, ejecutadas con un
rol sin privilegios de owner/superuser, sí quedan restringidas
correctamente.

Si Alembic corre las migraciones con el mismo usuario de Postgres que usa
FastAPI/SQLAlchemy en runtime (patrón común por conveniencia: un solo
`DATABASE_URL` para todo), ese usuario termina siendo el owner de las
tablas — y entonces RLS es cosmético: pasa cualquier prueba manual hecha
como ese mismo usuario, pero no protege nada en producción.

## Decisión

Se usan **dos roles de Postgres distintos y no intercambiables**:

| Rol | Uso | Privilegios |
|---|---|---|
| `sige_migrator` | Alembic (`alembic upgrade`), y solo eso. Nunca lo usa el proceso de FastAPI. | Owner de las tablas. `CREATEDB`/`CREATEROLE` no requeridos; sí necesita `CREATE`/`ALTER`/`DROP` sobre el schema `public`. |
| `sige_app` | Conexión runtime de FastAPI/SQLAlchemy (`core/session.py`), la que `core/security.py` usa para hacer `SET app.current_rol` / `SET app.current_personal_id` por request. | `SELECT, INSERT, UPDATE, DELETE` sobre las tablas vía `GRANT` explícito. **`NOSUPERUSER`, y no es owner de ninguna tabla.** Sin `CREATE`/`DROP`/`TRUNCATE`. |

`sige_app` es el único rol con el que el backend abre conexiones. Ningún
código de aplicación debe usar `sige_migrator` ni el superusuario de
Postgres (`postgres`) para servir requests — ese último se reserva para
bootstrap del contenedor y tareas manuales de operación.

### docker-compose (dev / staging)

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: ${DB_MIGRATOR_USER:-sige_migrator}
      POSTGRES_PASSWORD: ${DB_MIGRATOR_PASSWORD}
      POSTGRES_DB: ${DB_NAME:-sige}
    volumes:
      - pgdata:/var/lib/postgresql/data
      # Corre una sola vez, al crear el volumen: crea sige_app y le
      # otorga solo DML. No se re-ejecuta en containers ya inicializados
      # (limitación del entrypoint oficial de postgres) — en staging, si
      # el volumen ya existe, este GRANT se aplica vía la primera
      # migración de Alembic en vez de este script (ver más abajo).
      - ./db/init/01_create_app_role.sql:/docker-entrypoint-initdb.d/01_create_app_role.sql:ro
    ports:
      - "5432:5432"

  backend:
    build: .
    environment:
      # Usado por Alembic (alembic/env.py) — nunca por la app en runtime.
      DATABASE_URL_MIGRATIONS: postgresql://${DB_MIGRATOR_USER:-sige_migrator}:${DB_MIGRATOR_PASSWORD}@db:5432/${DB_NAME:-sige}
      # Usado por core/session.py — el único DSN que ve FastAPI.
      DATABASE_URL: postgresql://${DB_APP_USER:-sige_app}:${DB_APP_PASSWORD}@db:5432/${DB_NAME:-sige}
    depends_on:
      - db
```

`./db/init/01_create_app_role.sql` (montado en `docker-entrypoint-initdb.d`,
se ejecuta una vez con el rol `POSTGRES_USER` al crear el volumen):

```sql
CREATE ROLE sige_app LOGIN PASSWORD :'db_app_password' NOSUPERUSER NOCREATEDB NOCREATEROLE;
-- Las GRANT reales sobre tablas van en la primera migración de Alembic
-- (después de que las tablas existan), no aquí — este script solo crea
-- el rol para que exista antes de que Alembic corra su primer GRANT.
```

El `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES ... TO sige_app;`
vive como parte de la migración de Alembic que crea el schema (o de una
migración dedicada inmediatamente después), no en un script suelto —
así el privilegio del rol de runtime queda versionado junto con el
esquema al que aplica, igual que las políticas RLS de `db/ddl_mvp.sql`.

### Variables de entorno que controlan esto

| Variable | Rol al que corresponde | Quién la lee |
|---|---|---|
| `DB_MIGRATOR_USER`, `DB_MIGRATOR_PASSWORD` | `sige_migrator` | `docker-compose.yml` (bootstrap de `db`), Alembic vía `DATABASE_URL_MIGRATIONS` |
| `DB_APP_USER`, `DB_APP_PASSWORD` | `sige_app` | script de init (para crear el rol), backend vía `DATABASE_URL` |
| `DATABASE_URL_MIGRATIONS` | — | únicamente `alembic/env.py` |
| `DATABASE_URL` | — | únicamente `core/session.py` / `core/config.py` |

En **staging**, el patrón de dos roles es idéntico; lo único que cambia es
la fuente de `DB_MIGRATOR_PASSWORD` / `DB_APP_PASSWORD` — no van en un
`.env` versionado, se inyectan desde el secret manager del entorno (o
`.env.staging` fuera de git). El pipeline de CI/CD que corre
`alembic upgrade` usa `DATABASE_URL_MIGRATIONS`; el proceso de la app
(contenedor de FastAPI) solo recibe `DATABASE_URL`. Ningún pipeline debe
inyectar `DATABASE_URL_MIGRATIONS` al contenedor del backend.

## Razón

Es la única forma de que RLS deje de ser una capa decorativa: si el
usuario de runtime es owner o superuser, cada política de
`docs/rbac/matriz-rbac-mvp.md` es letra muerta independientemente de qué
tan bien esté escrito el SQL. Separar el rol que puede cambiar el esquema
(migraciones) del rol que puede leer/escribir filas (runtime) además
limita el radio de daño de una inyección SQL o un bug de la aplicación: en
el peor caso, `sige_app` nunca puede hacer `DROP TABLE` ni alterar una
política RLS.

## Alternativas descartadas

- **Un solo `DATABASE_URL` compartido entre Alembic y FastAPI**: descartado
  — es exactamente el escenario que se validó como inseguro (RLS
  bypasseada) al probar `db/ddl_mvp.sql` como el rol owner.
- **Usar `FORCE ROW LEVEL SECURITY` en vez de separar roles**: descartado
  porque no resuelve el caso — `FORCE` no tiene efecto sobre roles
  `SUPERUSER`, y el usuario del backend no debería ser owner de las tablas
  de todos modos (menor superficie de daño ante un bug o inyección SQL).
- **Un tercer rol intermedio de "admin de aplicación" con más privilegios
  que `sige_app` pero sin ser owner**: descartado para el MVP — el rol
  `admin` de negocio (tabla `Personal.rol`) ya se resuelve con RLS dentro
  de `sige_app`; no hay necesidad hoy de un privilegio de Postgres
  adicional para ese caso.

## Consecuencias

- `alembic/env.py` (cuando se implemente) debe leer `DATABASE_URL_MIGRATIONS`,
  no `DATABASE_URL`.
- `core/config.py` (cuando se implemente) debe exponer únicamente
  `DATABASE_URL` (el DSN de `sige_app`) al resto de la aplicación — no debe
  existir ninguna ruta de código donde el backend pueda conectarse como
  `sige_migrator`.
- La migración de Alembic que crea las 11 tablas debe incluir el
  `GRANT ... TO sige_app` como parte del mismo cambio versionado, para que
  un ambiente nuevo nunca quede con tablas creadas pero sin privilegios
  otorgados al rol de runtime (lo que rompería la app con "permission
  denied" en vez de fallar de forma insegura, que es el error correcto del
  lado seguro).
- Cualquier script de mantenimiento/soporte que necesite bypassear RLS
  intencionalmente (ej. una migración de datos masiva) debe conectarse
  explícitamente como `sige_migrator` y documentarlo, nunca cambiar los
  privilegios de `sige_app` para lograrlo.
